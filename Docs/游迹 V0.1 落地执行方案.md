# 游迹 V0.1 落地执行方案

## 一、方案目标

在不扩展地域、不增加新业务系统的前提下，先完成第一条可重复验证的产品闭环：

```text
用户输入需求
  → 系统解析为结构化行程请求
  → 检索贵州真实景区、酒店、餐厅、交通数据
  → 路线算法生成贵阳 → 安顺两日游
  → 预算和营业时间校验通过
  → 返回结构化行程 JSON
  → 用户保存、查看、局部调整
  → 其余行程保持不变
```

验收目标：

```text
贵阳 → 安顺（黄果树 / 龙宫 / 天龙屯堡）两日游
从 API 层稳定跑通，并有自动化测试证明。
```

## 二、明确不做

本阶段不做：

- 扩展到云南、重庆或其他省份
- 酒店、门票预订
- 社交、直播、视频、商城
- 多人协同
- 实时旅行管家
- AR、语音导游
- 商业化和佣金
- 微服务拆分
- Kafka、复杂事件驱动架构
- 重型 TSP/VRP 或 ML 路线算法
- 同时开发 Flutter、Next.js、Admin 三个完整前端

## 三、当前问题归纳

### 1. 结构问题

- 工作区根目录不是 Git 仓库，实际代码位于 `/Volumes/aigo S7 Med/项目/游迹/youpji`，版本管理边界不清。
- `backend/target` 约占 1.8GB，构建产物污染目录。
- 根目录和 `youpji` 下存在重复的 `package.json`、`scripts/seed.mjs`。
- 大量 `.DS_Store`。
- 后端拆成多个很薄的 crate，MVP 阶段维护成本偏高。

### 2. 产品问题

- 已经有大量接口和数据库表，但贵阳 → 安顺闭环没有端到端验证。
- `frontend/`、`admin/` 基本为空。
- 种子数据只有少量内容，无法证明路线规划质量。
- 测试数量为 0。

### 3. 架构问题

- `route` 中硬编码安顺、贵阳、黔东南等目的地。
- 预算目前更接近估算输出，不是严格硬约束。
- 交通和营业时间约束不足。
- AI 输出进入规划流程前缺少严格 schema 校验。
- 认证会话使用进程内 `HashMap`，不能支持重启和多实例。
- Redis、Ollama、AMAP、Scheduler 部分仍为占位。
- 领域 crate 直接依赖 `PgPool`，不利于测试替换。

## 四、目标架构

保持三个进程，不拆微服务：

```text
前端
  │
  ▼
Axum API
  ├── Auth / User
  ├── Catalog
  ├── Planning
  ├── Itinerary
  ├── Content
  └── AI Gateway
  │
  ├── PostgreSQL + PostGIS + pgvector
  ├── Redis
  ├── 地图/天气适配器
  └── 云端 LLM / 本地 Ollama
```

后台任务：

```text
Worker
  ├── 数据过期标记
  ├── 数据差异发现
  └── 审核队列生成

Scheduler
  ├── 天气刷新
  ├── 数据巡检
  └── 缓存失效
```

### Crate 收缩方案

将当前过细的领域 crate 收敛为：

```text
backend/crates/
├── common
├── auth
├── catalog
├── planning
├── itinerary
├── content
└── ai
```

映射关系：

```text
catalog
├── destination
├── attraction
├── hotel
└── restaurant

planning
├── route
├── recommendation
├── weather
└── external map adapter

itinerary
├── itinerary
├── user preferences
└── feedback
```

这样做的原因：

- 减少跨 crate 引用和样板代码
- 保持业务边界清晰
- 让核心规划逻辑集中
- 避免每个模块一个独立 crate 的过度工程化

- 放入 `warnings`

## 阶段 2：重构规划请求与 AI 边界

目标：把自然语言、AI、路线算法之间的职责明确分开。

### 2.1 统一结构化请求

统一规划请求结构：

```json
{
  "origin": "贵阳",
  "destination": "安顺",
  "start_date": "2026-10-01",
  "end_date": "2026-10-02",
  "days": 2,
  "people": 2,
  "budget": 3000,
  "transport": "self_drive",
  "interests": ["nature", "history"],
  "avoid": [],
  "intensity": "medium",
  "mode": "standard",
  "lodging_tier": "standard"
}
```

### 2.2 拆分解析器

```text
RuleParser
LlmParser
RequestValidator
```

职责：

- `RuleParser`：无外部依赖时的确定性降级方案
- `LlmParser`：可选地从自然语言提取字段
- `RequestValidator`：统一验证所有字段

### 2.3 增加严格验证规则

至少验证：

- `origin`、`destination` 非空
- 日期合法且 `end_date >= start_date`
- `days` 与日期匹配
- `people > 0`
- `budget > 0`
- `transport` 属于枚举
- `interests`、`avoid` 来自允许标签
- `mode` 属于 `economy | standard | comfort`
- `intensity` 属于 `low | medium | high`
- V0.1 目的地属于贵州范围

### 2.4 限制 LLM 权限

LLM 只能：

- 提取字段
- 解释行程
- 生成用户友好的说明文字

LLM 不能：

- 直接声明事实
- 决定票价
- 决定营业时间
- 决定天气
- 绕过路线算法生成行程节点

### 验收标准

```text
POST /api/v1/travel/parse
```

能够返回结构化请求，并覆盖：

- 安顺两日游
- 黄果树两日游
- 从贵阳出发
- 预算限制
- 自驾
- 自然景观
- 少走路
- 非法日期和非法预算

## 阶段 3：重写路线规划核心

目标：让路线规划从“按评分分配”升级为“按时间、预算、事实约束生成可执行路线”。

### 3.1 移除硬编码目的地

删除 `route` 内部类似以下逻辑：

```rust
if dest.contains("安顺") { ... }
else if dest.contains("贵阳") { ... }
```

改为：

```text
destination 关键词
  → destination_id
  → destination 关联景区
  → recall candidates
```

### 3.2 引入候选过滤

候选过滤必须覆盖：

- 目的地层级匹配
- 城市/区县匹配
- 景区关闭状态
- 用户 `avoid` 标签
- 用户兴趣匹配
- 开放时间冲突
- 交通时间约束
- 预算约束
- 景区重复

### 3.3 使用统一评分

评分维度：

```text
景观价值
兴趣匹配
景区质量
攻略热度
季节适合度
时间匹配
距离成本
时间成本
预算成本
疲劳成本
```

输出必须保留：

```text
score
reason
candidate_source
```

### 3.4 增加真正的时间轴

每个行程节点至少包含：

```text
time
location
distance
duration
cost
reason
notice
```

每天必须检查：

- 景区开放时间
- 景区关闭时间
- 交通耗时
- 午餐时间
- 晚餐时间
- 酒店入住时间
- 返程时间
- 强度上限

### 3.5 预算改为硬约束

预算拆分：

```json
{
  "limit": 3000,
  "transport": 400,
  "lodging": 800,
  "tickets": 500,
  "food": 600,
  "parking": 100,
  "other": 100,
  "reserve": 500,
  "total": 3000
}
```

如果：

```text
total > limit
```

必须返回：

```json
{
  "code": "BUDGET_EXCEEDED",
  "message": "当前预算无法生成满足硬约束的行程"
}
```

不能静默超支。

### 验收标准

对以下输入：

```text
贵阳 → 安顺
2 天
2 人
预算 2000
自驾
黄果树、龙宫、天龙屯堡
```

系统必须稳定生成：

- 至少包含 3 个核心景区
- 两天顺序合理
- 不重复安排同一景区
- 景区营业时间不冲突
- 交通时间不重叠
- 预算不超限
- 输出结构化 JSON
- 附带必要的 `warnings`

## 阶段 4：实现局部重规划

目标：严格遵守“改单点只重算受影响部分”。

### 4.1 定义编辑操作

V0.1 只支持：

```text
remove_item
replace_restaurant
move_item_to_day
replace_hotel
```

请求结构：

```json
{
  "itinerary_id": "uuid",
  "edit_op": {
    "type": "remove_item",
    "item_id": "uuid"
  }
}
```

### 4.2 返回影响范围

响应必须包含：

```json
{
  "changed_days": [1],
  "unchanged_days": [2],
  "diff": {
    "removed": [],
    "added": [],
    "updated": []
  },
  "warnings": []
}
```

### 4.3 禁止整体重生成

除以下情况外，不允许重新生成全部行程：

- 数据源变化导致整个行程不可执行
- 用户修改了目的地、日期、人数、预算、交通方式等全局参数

### 验收标准

删除第一天一个景区后：

- 第二天行程节点不变
- 只有受影响时间段重新计算
- 预算重新计算
- 返回明确的 `changed_days`

## 八、最终验收标准

V0.1 第一条闭环必须同时满足：

## 九、执行原则

```text
先清理工程
→ 先补事实数据
→ 先写硬约束测试
→ 再优化算法
→ 再补 API
```
