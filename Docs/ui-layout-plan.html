游迹 App UI 布局规划

V0.1 只围绕一条闭环：贵阳 → 安顺（黄果树 / 龙宫 / 天龙屯堡）两日游。布局目标不是「把 12 个页面都摆出来」，而是让用户在 3 次点击内从「我想去安顺玩两天」走到一份可以照着执行的行程，并且每一项事实都看得见来源与核验状态。

5 个底部 Tab 12 页收敛为 9 个必做 核验状态可见 不直连任何 LLM

信息架构

底部 5 个 Tab 覆盖全部二级入口。酒店、餐厅、地图不占 Tab——它们在 V0.1 里只以「行程内的项」和「探索的筛选维度」两种形态出现，独立 Tab 会诱导用户脱离行程去比价。

主线三屏线框

这三屏构成 V0.1 的验收路径。其余页面都是这三屏的下钻或旁路，不需要独立设计投入。

贯穿全 App 的四条硬规则

这四条是 UI 层对 DESIGN.md 数据契约的直接投影，不是设计偏好。违反任意一条，页面就退化成「攻略搬运站」。

1 · 核验徽章常驻，不做隐藏

verified 已核验 pending 待核验 stale 需更新 disputed 有冲突

任何展示门票 / 开放时间 / 价格 / 营业时间的卡片，右上角必须有徽章。点击展开来源、source_time、last_verified。unverified 一律不落在卡片正文，只进提醒区——这是铁律 4 的 UI 落点。

2 · 预算永远是双数字

已分配
¥1,240
硬上限
¥1,500

只显示一个数字，用户无法判断方案是否还留了余地。降级发生时（plan_degraded）在预算条上直接标出被调整的项，而不是塞进提醒列表。

3 · 局部重规划用 diff 呈现

D2 已调整 D1 未变更

响应里的 changed_days / unchanged_days / diff 要在改完后作为一张对照卡给用户看：「你删了龙宫 → D2 改成 X，D1 一个字没动」。这是铁律 8 唯一可信的用户可见证据。

4 · 生成过程可见，不做假进度条

  • 解析需求 → 召回景区 → 计算路线 → 按天装包 → 预算校验
  • 五步对应后端管线，命名与 DESIGN.md 保持一致
  • 生成中允许先返回候选项，边出边看，而不是空转 15 秒
